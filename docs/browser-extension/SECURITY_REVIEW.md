# Security review checklist

Maps DESIGN.md's threat model (section 6.4) to what is actually built and tested, in the same honest-ledger style as
this project's `CHANGELOG.md` and `docs/agents/ROADMAP.md` — a claim here means it was checked in this repo, not that
a third party has audited it. Re-read this before a store submission or a security-sensitive change; update it in the
same commit as whatever it describes changes.

| Threat | Mitigation | Status |
|---|---|---|
| A malicious web page sends messages to the extension, or forges a command | `chrome.runtime.onMessage` checks `sender.id === chrome.runtime.id`; there is no `externally_connectable`; a content script only answers messages shaped `{abp: 1, ...}` from the extension's own background, never a page-origin `postMessage` | **Built, tested** — `src/content/index.ts`'s listener rejects anything without a matching sender id; covered indirectly by the real-Edge E2E suite driving a hostile fixture page. |
| Local malware, or another local user, connects to the bridge | `bot/browser_bridge.py`: loopback-only (`is_loopback`), an extension-`Origin` allow-list, a pairing key, per-server id pinning, brute-force lockout on pairing codes | **Built, tested** — `tests/test_browser_bridge.py` (31 tests) covers pairing, lockout, origin checks and pinning directly. |
| A web page prompt-injects the agent | Untrusted-content envelope (`ext_browser.py`'s `<untrusted_page_content>` wrapper), taint on reading an untrusted host, approval required to act afterward, the sensitive-site blocklist, no secret access from page content | **Built, tested** — `tests/test_ext_browser_tools.py` includes a fixture page containing a literal prompt-injection string and asserts it is wrapped as data, not executed. |
| A compromised or buggy ABP server drives the browser beyond the person's intent | Every rule above is **also** enforced inside the extension itself (`src/background/policy.ts`'s `Enforcer`), not only server-side — grants, the sensitive blocklist, rate limits, the always-ask set, and the on-page Stop control all work even if the server side is fully compromised | **Built, tested** — `tests/unit/policy.test.ts`, `urlpolicy.test.ts`; the real-Edge E2E suite's safety-case tests exercise the extension with no server-side check at all by calling its router directly. |
| Extension supply chain | Deps are ordinary pinned npm packages (`package-lock.json`), no remote code is fetched at runtime, the build is deterministic given the same lockfile, `THIRD_PARTY_NOTICES.md`/`sbom.json` list everything shipped | **Partly built.** Pinned deps and an SBOM: yes. **Not built:** a *signed* store release (needs a real Chrome Web Store / AMO signing identity this repo cannot hold) and CI-verified build reproducibility across machines — both are process, not code, and belong to whoever actually submits a release. |
| Model download tampering (in-browser models, phase 3) | HTTPS-only sources (Hugging Face Hub, MLC's prebuilt list); a format allow-list (no pickled/`.bin` torch files reach the browser — WebLLM and transformers.js only load their own compiled/ONNX formats) | **Inherited from the runtimes, not independently verified by ABP code.** WebLLM and transformers.js each fetch and cache their own weights (see `src/models/catalog.ts`'s comment on why ABP does not duplicate this); this repo does not itself re-verify a sha256 against the Hub's LFS metadata the way the original design sketched — that check exists inside the libraries, and this session did not audit their source to confirm it. Treat this as **unverified** until someone reads or tests that code path directly. |
| XSS in an extension page (popup/options/side panel) | Strict CSP (`script-src 'self' 'wasm-unsafe-eval'; object-src 'self'`), no inline `<script>`, every options/popup page built with `document.createElement`/`textContent` (`src/shared/ui.ts`'s `el()`) — a page-derived string is never assigned to `innerHTML` anywhere in this codebase | **Built, tested** — grep-verifiable (no `innerHTML` assignment of untrusted data exists in `src/`); the CSP itself is asserted by `esbuild.config.mjs` writing the same fixed policy into every manifest. |
| Adapter hijack (a fake update swaps a web-session adapter's selectors to exfiltrate data) | Adapters are declarative JSON (`src/adapters/*.json`), interpreted by fixed, reviewed code (`src/content/webengine.ts`) that can only click/read within the adapter's own `hosts`; there is no code path that lets an adapter run arbitrary script or navigate outside its declared hosts | **Built, narrower than designed.** The "signed, independently-updatable adapter" mechanism DESIGN.md originally sketched (Ed25519-signed data updates pushed separately from an extension release) was **not built** — adapters ship only as part of an ordinary extension release, so they carry exactly the same trust and review process as the rest of the code, not a separate signed channel. This is a real, deliberate scope reduction, not an oversight: it removes an entire signing/verification subsystem in exchange for one less independent update path, and should be revisited before treating a compromised extension-release pipeline and a compromised adapter-update pipeline as separate risks. |

## What this review does **not** cover

- A real penetration test or third-party audit — none has been done.
- Live behavior on the actual chat websites (`web/grok` etc.) or actual WebGPU/model-download hardware — every
  automated test here uses a fake extension, a fixture page, or jsdom (see each phase's own CHANGELOG entry for
  exactly what was and was not run live).
- The native-messaging host's real registry/manifest registration (`scripts/install_native_host.py`) — only its pure
  logic was tested; installing it for real was deliberately not done in this session (see CHANGELOG phase 4).
- Anything about the Chrome Web Store / AMO review process itself, code-signing keys, or account security for
  whoever actually publishes a release.
